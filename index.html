The address bar

S3 stores keys, not folders — a folder is just a shared key prefix. The bar at the top is the real thing: click it or press ⌘L and type any bucket/prefix/ to jump straight there. Naming a different bucket switches to the matching connection.

CORS rules

A browser cannot read a bucket that does not allow it. In the AWS console under S3 → your bucket → Permissions → CORS, paste: 
[{
  "AllowedHeaders": ["*"],
  "AllowedMethods": ["GET","PUT","POST","DELETE","HEAD"],
  "AllowedOrigins": ["*"],
  "ExposeHeaders": ["ETag"]
}]
Narrow AllowedOrigins to the exact origin serving this page once it works.

Permissions to grant

s3:ListBucket, s3:GetObject, s3:PutObject, s3:DeleteObject — scoped to the one bucket.

Where credentials live

Nothing is kept in this browser. Credentials sit in sessionStorage for this tab and disappear when you close it, so a stolen or synced browser profile holds no keys.

Save encrypted to file, load from file

Save encrypted to file writes your connections to a .s3vault file: AES-256-GCM, key derived from a passphrase you choose with PBKDF2-HMAC-SHA256 at 310,000 iterations, random 16-byte salt, fresh IV per save. The file is unreadable without the passphrase, so it is safe to back up or carry between machines. Load from file decrypts in memory and either adds to your list or replaces it. A wrong passphrase or an edited file fails to decrypt rather than loading anything.

What encryption does not cover

While you are connected the plaintext keys are in page memory, so anything running in this page can read them — XSS, a browser extension, or a tampered CDN script (the AWS SDK loads from sdk.amazonaws.com). A leaked file cannot be revoked either: changing the passphrase does not help, because the old copy still opens with the old one. If a file goes missing, rotate the S3 keys themselves. Scope credentials to one bucket, grant the four actions above and nothing more, and keep the file where you would keep a password database.
